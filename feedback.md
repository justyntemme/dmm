# Feedback

## Mobile Web App

- Make the mobile app game-first.
- Do not default-select a game.
- Default mobile view should be a clean game library/list.
- Clicking a game should open that game's menu/screen.
- After a game is open, keep game navigation available through a compact menu/list instead of putting the entire game list below the selected game content.
- User flow should be: find/search game, click game, then use the newly shown Add Mod/import element inside that game.
- Fetch and show game images for each game.
- Only expose Nexus URL import from inside a selected game screen/menu.
- Do not expose dependency management in the mobile app.
- Do not expose server settings in the mobile app.
- Break the app into tabs with a header bar instead of one scrolling page.
- Keep Jobs in its own tab.

## MVP Import Scope

- MVP import testing must use Nexus files that support Mod Manager Download / `nxm://` automatic manager links.
- Plain manual-install mods with only extract/copy instructions are post-MVP unless they are also available through the automatic Nexus manager flow.
- Prototype-style custom/manual handlers are post-MVP game modules and should not be used as proof of the automatic Nexus MVP path.
- Non-premium Nexus API keys can list files, but download-link resolution requires the `nxm://` link parameters generated by the Mod Manager Download button.
- Plain Nexus mod URLs should be used to browse/select files, then the user must paste the matching `nxm://` automatic link unless the account/API path can resolve direct download links.

## Decky Plugin

- Move dependency status to the Decky plugin on the Steam Deck.
- Add a Decky plugin settings tab for server settings.
- Decky plugin tab buttons are too wide; use narrower, more polished segmented/tab controls.
- Dependency rows must not clip text, and the Dependencies view needs professional alignment and scroll behavior.
- The Decky dependency/server tab buttons became too small and are no longer easy to navigate.
- Prefer one Decky button per row unless the button text is very short.
- The two-column Allow Tunnel row appears to be the main Decky navigation/layout culprit.
- Decky dependencies must remain reachable/navigable from controller input.
- In Decky Mod Manager, dependency status should live in the Debug tab, not Settings.
- Add "Auto-accept download requests" as a Decky Settings checkbox.
- Remove the auto-accept download control from the phone/tablet web app.
## MVP UI/UX Review: Mod Management

- Deployment UI is not acceptable for MVP as-is. We need to rethink the mod-management experience before calling the app usable.
- Review how strong mod managers present downloads, approvals, install state, enabled/disabled mods, profiles, deployment preview, conflicts, deploy, purge, and repair.
- This review belongs in the MVP workstream, not as post-MVP cleanup. The first usable release should have a deliberate mod-management model and polished deployment flow.
- Look across current mod managers before finalizing the flow, then keep the best patterns that fit Decky Mod Manager's phone-first Steam Deck experience.
- Treat UI polish as product architecture, not a final cleanup pass. The core flows should be designed around the user journey from the start.
- Download approvals should clearly communicate what was captured, what will happen on approval, and whether the archive is immediately deployable, needs installer choices, or is blocked by unsupported install planning.
- The primary mod-management surface should be a selected profile's mod list, not a staging/deployment dashboard.
- Default profile should be selected by default, and profile switching should make it obvious which mod list is being edited.
- Simple users should download a mod, approve the download when approval is required, see the mod in the selected profile, and enable/disable it with a straightforward toggle.
- Add a setting for automatic download approval. It must be off by default, so approval is required unless the user opts into the faster flow.
- Add Decky notifications for Nexus request capture and install/download transitions. After Nexus says a download is starting, the user must get visible DMM feedback in Gaming Mode instead of silence.
- Auto-deploy should pause on FOMOD/installer-choice mods unless the user has already approved a compatible saved preset.
- Hide staging, install planning, target mappings, manifests, deployment transactions, purge, repair, and file-level preview behind advanced/power-user controls unless a conflict or error requires attention.
- Deployment should not feel like a raw file-operation debug page. It should show profile state and "Apply profile changes" first, with file-level detail available as an advanced drill-down.
- The UI should explain whether changes are already applied to the game or pending, without forcing the user to understand how symlinks/staging work.
- Overall mod management should prioritize user confidence: clear state labels, obvious next actions, safe defaults, and no ambiguous buttons that can mutate the game folder without context.

## Launch Tool UX

- SMAPI launch setup should be presented as a required runtime action for Stardew, not as a generic debug/file-editing feature.
- The Decky plugin may apply Steam launch options because it has access to Steam frontend APIs, but the Go backend should own the desired state and verification.
- The UI should explain that DMM will configure Steam to launch SMAPI for Stardew profiles that need it.
- Windows/Proton Stardew support is MVP, so launch setup must show which runtime was detected and which SMAPI executable will be used.
